Named 쿼리 : JPQL 쿼리문에 이름을 부여
→ 쿼리문 이름을 가지고 여기저기에 [재사용] 가능(추후에 설명하겠지만, 이 재사용성이 어마어마한 이점을 가져다 준다)
※Named 쿼리는 정적 쿼리(추후에 설명하겠지만, 쿼리문을 if문을 가지고 동적으로 쿼리문을 짜르거나 붙이거나 하는 동적 쿼리문은 작성 불가)

ex)
@Entity
@NamedQuery(
	name = "Member.findByUsername",// JPQL 쿼리문 별칭
	query = "select m from Member m where m.username = :username" // 실제 쿼리문(여기에서 if문 사용으로 동적 쿼리문 작성 불가)
)
public class Member{....}

List<Member> resultLIst = em.create[NaemdQuery]("Member.findByUsername", Member.class) // "Member.findByUsername" : JPQL 쿼리문의 별칭!!
				.setParameter("username", "회원1")
				.getResultLIst();


Named 쿼리의 어마어마한 장점
-> 위에서 쿼리문 [재사용]이 장점이라고 언급했는데, 정확히는 【애플리케이션 로딩 시점】에 초기화(JPQL 파싱)된 후 재사용 된다는 점이다. 
위 장점은 궁극적으로 애플르케이션 로딩 시점, 즉 "컴파일 타임"에 쿼리를 검증할 수 있다는 것이다.(이건 Naemd 쿼리가 정적 쿼리이기 때문에 가능한 것이다. 만약에 동적 쿼리문이였으면
애플리케이션 로딩 시점에 쿼리를 검증할 수가 없다)
우리가 주구장창 말해 왔듯이, 가장 좋은 에러는 컴파일 타임, 혹은 빌드 타임 에러이다. 


XML을 통해서 Named 쿼리를 정의할 수가 있다. 
ex)
[META-INF/ormMember.xml]
<?xml version="1.0" encoding="UTF-8"?>
<entity-mappings xmlns="http://xmlns.jcp.org/xml/ns/persistence/orm" version="2.1">
 <named-query name="Member.findByUsername">
 <query><![CDATA[
 select m
 from Member m
 where m.username = :username
 ]]></query>
 </named-query>
 <named-query name="Member.count">
 <query>select count(m) from Member m</query>
 </named-query>
</entity-mappings>

특징
1. @NamedQuery로 이미 네임드 쿼리가 정의돼 있어도, XML이 우선권을 가진다. 

2. 서버마다 매핑된 쿼리문이 살짝 다를 때 매우 유용
-> 여러 서버가 있고, 각 서버마다 Member.count라는 네임드 쿼리를 사용하고 있다고 하자. 
그런데 어느 날 요구사항이 바뀌어 어느 특정 서버에서 Member.count에 매핑된 JPQL 쿼리문을 바꿔야 한다고 하자. 
그러면 XML의 Member.count라는 네임드 쿼리에 매피이된 JPQL을 바꿔서 그 서버에 넣어 주기만 하면 된다. 
개인적으로 이런 유연성 덕분에 XML로 네임드 쿼리를 사용하는 게 더 좋은 것 같다. 
그리고 네임드 쿼리 목록을 XML에 한 곳에 묶어 두면 개발자도 편할 것 같다. 
김영한 왈 : 엔티티 위에 @NamedQuery를 쓰면 코드가 지저분 해져서 본인도 그 방식은 별로 선호하지 않는다고 한다. 
그리고 나중에 Spring Data JPA를 사용하게 되면 @Query를 써서, XML을 사용하지 않으면서, 엔티티 위에 지저분하게 네임드 쿼리를 쓰지 않아도,
 똑같이 JPA의 네임드 쿼리를 장점을 사용 가능하다고 하며, Spring Data JPA를 사용하는 편이라고 한다.
